# arcade-matter-mcp: Specification

Status: draft for review

This document describes what this repository will build: an MCP server that exposes the
[Matter API](https://docs.getmatter.com/api) as agent tools, hosted on Arcade Cloud with
[Arcade Deploy](https://docs.arcade.dev/en/build/arcade-deploy) and used through an
[Arcade MCP Gateway](https://docs.arcade.dev/en/operate/governance/mcp-gateways).

[Matter](https://getmatter.com) is a read-later app: you save articles, newsletters,
podcasts, PDFs and tweets, read them, and highlight passages. The API lets you read and
organize that library.

## Goals

- **Arcade hosts the server.** The only deployment target is `arcade deploy`. This repo
  contains no Dockerfiles, self-hosting instructions or infrastructure code.
- **One Matter library per deployment.** Each deployment authenticates with a single Matter
  personal API token, stored as an Arcade secret. See
  [Authorization model](#authorization-model).
- **Follow Arcade's documented patterns.** Use the conventions in the Arcade docs for
  project layout, secrets, tool metadata, errors and evals.
- **Tools built for agents, not a thin API wrapper.** Responses are trimmed to what a
  model needs, long article text is bounded, and composite tools answer common questions
  ("what did I highlight this week?") without the model chaining many calls.
- **Respect Matter's rate limits.** Matter may suspend tokens that ignore `Retry-After`,
  so the client honours it and tools keep API calls to a minimum.

## Non-goals

- Self-hosting, or running the server anywhere other than Arcade Cloud.
- **Multiple users.** Matter has no OAuth, and Arcade secrets are scoped to the
  organization or project, not to each end user. Everyone who can call this server acts
  on the library of whoever deployed it. Supporting other users would need OAuth from Matter or a
  per-user token store; both are out of scope for v1.
- Creating highlights. Matter's API can list, annotate and delete highlights, but not
  create them.
- Managing feeds and newsletter subscriptions, reordering the queue, or moving items
  back to the inbox. The API doesn't support these.
- Sync and caching. Arcade-hosted workers keep no state between calls.
- Matter's older, undocumented API (`api.getmatter.app/api/v11`, used by the Obsidian
  plugin). Only the public v1 API is used.

## Architecture

```text
MCP client ──► Arcade MCP Gateway ──► arcade_matter (Arcade Cloud) ──► api.getmatter.com/public/v1
                     │                          │
                     │                          └─ requires_secrets=["MATTER_API_TOKEN"]
                     └─ who may call the server     token injected via Context
                        (Arcade Auth mode)
```

1. **Matter API token.** Generated by whoever deploys the server, at
   [web.getmatter.com/settings](https://web.getmatter.com/settings). It starts with
   `mat_` and needs an active Matter Pro subscription.
2. **Arcade secret `MATTER_API_TOKEN`.** Uploaded by `arcade deploy` (from `.env`) or set
   with `arcade secret set`. Arcade injects it into each tool call; the model never sees
   it.
3. **This server.** Deployed with `arcade deploy`. Every tool declares
   `requires_secrets=["MATTER_API_TOKEN"]` and reads the token with
   `context.get_secret(...)`.
4. **MCP Gateway.** Picks which tools to expose and who may call them.

### Authorization model

- **Personal API token only.** Matter's OpenAPI spec defines a single bearer-token scheme
  (`mat_` prefix). It has no OAuth endpoints, so Matter can't be an Arcade OAuth
  provider.
- **One active token per Matter account.** Generating a token revokes the previous one
  immediately. Reuse an existing token, or update every
  integration that uses it (for example `matter-cli`) after generating a new one.
- **No scopes.** The token has full read and write access.
- **Access control happens at the gateway.** Every tool carries `ToolMetadata` behavior
  flags (`read_only`, `destructive` and so on). A read-only gateway is built by selecting
  only the read tools. Because the token is shared, the gateway should be limited to the
  token's owner (**Arcade Auth** mode, in a project with no other members).
- **Rate limits are per token.** Every caller shares one quota (see
  [Rate limits](#rate-limits)).

## Setup (one-time, for each deployment)

1. Generate a Matter API token: **web.getmatter.com/settings → Generate API Token**.
2. Put it in `.env` (never committed) as `MATTER_API_TOKEN=mat_...`.
3. Run `arcade login`.
4. Deploy with `arcade deploy -e src/arcade_matter/server.py`. Deploy uploads the values
   of the secrets the tools declare from `.env`. To rotate the token later without
   redeploying, run `arcade secret set MATTER_API_TOKEN=mat_...`.
5. Create an MCP Gateway in the Arcade dashboard, select the tools, and choose **Arcade
   Auth** mode. Connect clients to `https://api.arcade.dev/mcp/<gateway-slug>`, or run
   `arcade connect claude-code --gateway <gateway-slug>`.

For local testing, run the server over stdio. Arcade's local HTTP transport doesn't serve
tools that need secrets.

## Matter API summary

- **Base URL:** `https://api.getmatter.com/public/v1`. JSON bodies; every object has an
  `object` field. IDs are prefixed (`itm_`, `ann_`, `tag_`, `aut_`, `rs_`, `act_`).
  Timestamps are ISO 8601 UTC.
- **Lists:** `{object: "list", results, has_more, next_cursor}`, with an opaque `cursor`
  and `limit` from 1 to 100 (default 25).
- **Item statuses:** `inbox` (feeds and newsletters), `queue` (reading list) and
  `archive` (finished). An item can't be moved back to `inbox`.
- **Saving is asynchronous.** `POST /items` returns right away with
  `processing_status: "processing"`; extraction usually finishes in 20 to 60 seconds.
  Saving a URL that's already in the library returns the existing item (200, not 201).
- **Errors:** `{"error": {"code", "message", "field"}}`. The docs and the OpenAPI
  examples use different `code` values, so the client keys on the HTTP status. A 404 is
  also returned for resources owned by another account.
- **Versioning:** changes within v1 are additive. Deprecations come with a `Sunset`
  header and at least six months' notice.

### Rate limits

Per token, reported on each response in `X-RateLimit-Limit`, `-Remaining` and `-Reset`:

| Bucket | Limit | Counts |
|---|---|---|
| read | 120 / min | every `GET` |
| write | 30 / min | `POST`, `PATCH`, `DELETE` |
| save | 10 / min | `POST /items` |
| search | 30 / min | `GET /search` |
| markdown | 20 / min | `GET /items/{id}?include=markdown` (also counts as a read) |
| burst | 5 / sec | everything |

A 429 includes `Retry-After` (seconds). Matter's docs warn that clients ignoring it may
have their tokens suspended.

## Project layout

Mirrors [arcade-ynab-mcp](https://github.com/laughnan/arcade-ynab-mcp) and Arcade's guide,
[Organize your MCP server and tools](https://docs.arcade.dev/en/build/create-tools/tool-basics/organize-mcp-tools).

```text
src/arcade_matter/
├── server.py           # MCPApp("matter"), registers tool modules, app.run() under __main__
├── client.py           # Matter HTTP client: base URL, bearer auth, retries, error mapping
├── shaping.py          # trims API objects into model-friendly dicts
└── tools/
    ├── __init__.py
    ├── _common.py      # secret name, ToolMetadata presets, shared parameter types
    ├── account.py      # account, reading sessions
    ├── items.py        # list, get, content, save, update, delete
    ├── search.py
    ├── highlights.py   # annotations
    ├── tags.py
    └── insights.py     # composite tools
tests/
├── conftest.py         # httpx.MockTransport fake of the Matter API
└── test_*.py
evals/
└── eval_*.py           # arcade evals suites
docs/
└── SPEC.md
```

- `server.py` stays thin. Tools are defined with `@tool` in `tools/` modules and
  registered with `app.add_tool(...)`. As in arcade-ynab-mcp, it doesn't use
  `app.add_tools_from_module(...)`, which only works for top-level packages.
- `server.py` keeps `app.run()` inside `if __name__ == "__main__":`, which
  `arcade deploy` requires.
- The app is named `matter`, so tools are exposed as `Matter.ListItems` and so on
  (`Matter_ListItems` to MCP clients).

## Design rules

These apply to every tool.

1. **Auth.** Every tool uses `requires_secrets=["MATTER_API_TOKEN"]` and builds its
   client from `context`. A missing token raises a `ToolExecutionError` that says how to
   set the secret.
2. **Metadata.** Every tool declares `ToolMetadata` with
   `Classification(service_domains=[ServiceDomain.DOCUMENTS])` and a `Behavior` with
   `operations` and all four flags (`read_only`, `destructive`, `idempotent`,
   `open_world=True`) set explicitly.
3. **Vocabulary.** Tools use Matter's app terms: "highlights" for API annotations,
   "queue", "inbox" and "archive" for statuses. Parameter descriptions name the API
   field where it differs.
4. **Response shaping.**
   - Keep IDs so the model can chain calls.
   - Flatten nested objects (`author` becomes the author's name; `tags` becomes a list of
     `{id, name}`).
   - Drop fields agents don't need (`object`, `image_url`, `library_position`,
     `inbox_position`) and omit keys whose value is `null`.
   - Report `reading_progress` as a whole percentage.
   - Treat `content_type` as an open string; the docs and the OpenAPI enum disagree.
5. **Bounded output.**
   - List tools take `limit` (default 25, max 100) and an optional `cursor`, and return
     `next_cursor` when there are more results. No tool silently fetches every page.
   - `GetItemContent` returns at most `max_chars` of Markdown (default 20,000), with
     `offset` for continuing and `truncated: true` when more remains.
6. **Few API calls.** Single-purpose tools make one request. Composite tools make at most
   a small, fixed number, stated in their description, and issue them one at a time to
   stay under the burst limit.
7. **Rate limits.** On a 429, the client waits and retries once if `Retry-After` is 5
   seconds or less (burst limit). Otherwise it raises `UpstreamRateLimitError` with
   `retry_after_ms`. It never retries without waiting.
8. **Errors.** Use the classes in `arcade_mcp_server.exceptions`, keyed on HTTP status:
   - 400 / 422: `RetryableToolError` with Matter's message and `field`.
   - 401: `ToolExecutionError`. The token is invalid or was revoked (generating a new one
     revokes the old); update the `MATTER_API_TOKEN` secret.
   - 403: `ToolExecutionError`. The API needs an active Matter Pro subscription.
   - 404: `RetryableToolError`. Look up valid IDs with a list or search tool.
   - 409: `RetryableToolError`. For example, renaming a tag to a name that exists.
   - 429: see rule 7. Other statuses: `UpstreamError`.
9. **Writes are explicit.** Write tools take exact IDs. Delete tools are tagged
   destructive and never infer their target from a vague request.

## Tool catalog

Each table lists the Matter endpoints the tools call.

### Phase 1: Read-only core

These are read-only, idempotent and non-destructive.

| Tool | Endpoint | Parameters | Returns |
|---|---|---|---|
| `GetAccount` | `GET /me` | none | name, email, account creation date and rate limits |
| `ListItems` | `GET /items` | `status` (`queue` default, `inbox`, `archive`, `all`), `is_favorite`, `tag_ids`, `content_type`, `updated_since`, `order` (`updated`, `library_position`, `inbox_position`), `limit`, `cursor` | items: ID, title, URL, site, author, status, content type, word count, progress, favorite, tags, excerpt, `updated_at` |
| `GetItem` | `GET /items/{id}` | `item_id` | one item, with its processing status |
| `GetItemContent` | `GET /items/{id}?include=markdown` | `item_id`, `max_chars`, `offset` | the item's Markdown text, bounded (see rule 5). Uses the `markdown` bucket |
| `SearchLibrary` | `GET /search?type=items` | `query` (2+ characters; supports `"phrase"`, `-term`, `by:`, `site:`, `title:`), `status` (`queue`, `archive`), `limit`, `cursor` | items ranked by relevance |
| `ListHighlights` | `GET /items/{id}/annotations` | `item_id`, `limit`, `cursor` | highlights: ID, text, note, created and updated dates |
| `ListTags` | `GET /tags` | `limit`, `cursor` | tags with item counts |
| `ListReadingSessions` | `GET /reading_sessions` | `since`, `limit`, `cursor` | daily reading time, newest first |

### Phase 2: Writes

| Tool | Endpoint | Behavior |
|---|---|---|
| `SaveItem` | `POST /items` | create, idempotent (saving a URL twice returns the existing item). `url` (http or https), `status` (`queue` default, or `archive`). Returns right away; the response says whether extraction is still processing and to check `GetItem` later |
| `UpdateItem` | `PATCH /items/{id}` | update, idempotent. `status` (`queue` or `archive`), `is_favorite`, `reading_progress` (0 to 100 percent). At least one field required |
| `AddTag` | `POST /items/{id}/tags` | update, idempotent. Adds a tag by name (case-insensitive), creating it if needed |
| `RemoveTag` | `DELETE /items/{id}/tags/{tag_id}` | update, idempotent. Removes a tag from one item; the tag itself is kept |
| `SetHighlightNote` | `PATCH /annotations/{id}` | update, idempotent. Sets a highlight's note; an empty string clears it |
| `RenameTag` | `PATCH /tags/{id}` | update, idempotent. Renames a tag everywhere. 409 if the name is taken |
| `DeleteItem` | `DELETE /items/{id}` | delete, destructive. Permanently deletes an item with its highlights and tags |
| `DeleteHighlight` | `DELETE /annotations/{id}` | delete, destructive |
| `DeleteTag` | `DELETE /tags/{id}` | delete, destructive. Removes the tag from every item |

### Phase 3: Composite tools

These are read-only.

| Tool | Answers | Built from |
|---|---|---|
| `GetItemWithHighlights` | "What did I highlight in this article?" The item, its highlights and notes | `GetItem` + one page of highlights (2 requests) |
| `ListRecentHighlights` | "What did I highlight this week?" Highlights grouped by item, for items updated since a date | one page of items by `updated_since` + highlights for up to `max_items` items (default 10, max 20), so at most 21 requests. Items whose highlights are older than `since` are left out |
| `SummarizeReadingTime` | "How much have I read this month?" Total and average time per day, days read, longest streak, busiest day | reading sessions since a date, up to 4 pages |

## Testing

- **Unit tests (pytest):** mock Matter with `httpx.MockTransport`, using response bodies
  built from the examples in Matter's OpenAPI spec. Tests never call the real API and
  never use real library data. Cover: request shapes, response shaping, error mapping,
  the 429 retry rule, content truncation and the composite tools' grouping and math.
- **Server tests:** every tool is registered, requires `MATTER_API_TOKEN`, declares
  metadata, and read tools are read-only.
- **Tool evals (`arcade evals`):** suites in `evals/` check that models pick the right
  tool with the right arguments. Examples: "What's in my queue about AI?" should call
  `SearchLibrary`; "Archive that article" should call `UpdateItem` with
  `status="archive"`.
- **Manual end-to-end testing:** run the server locally over stdio with the token in
  `.env`, then deploy and call it through the gateway.

## Delivery plan

The raw `arcade new arcade_matter` output is the first commit on `main`. Each step below
is a separate pull request.

1. **This specification.**
2. **Foundations.**
   - Remove the sample tools (`greet`, `whisper_secret`, `star_repo`).
   - Add `client.py`, `shaping.py` and `tools/_common.py`, the test harness and CI.
   - Fix `pyproject.toml`: description, and align ruff and mypy targets with
     `requires-python`.
   - Replace the sample secret in `.env.example` with `MATTER_API_TOKEN`.
   - Write the README.
3. **Phase 1 read tools** with tests.
4. **First deploy:** set the secret, `arcade deploy`, a read-only gateway, and an
   end-to-end check.
5. **Phase 2 write tools** with tests.
6. **Phase 3 composite tools** with tests and evals.

## Open questions

1. **Token sharing.** Should the setup steps tell deployers to reuse a token they already
   use elsewhere (for example in `matter-cli`)? Generating a new one revokes the old.
2. **Waiting for saves.** Should `SaveItem` optionally poll until extraction finishes
   (up to about 60 seconds, using read quota), or always return right away?
3. **Separate read and write gateways.** Should the recommended setup be a read-only
   gateway plus a separate gateway that includes the write and delete tools?
4. **`status=all`.** Matter doesn't say whether it includes items with no status. Check
   against the live API in step 4.
5. **Python version on Arcade Cloud.** `requires-python` is `>=3.10`. Confirm which
   version Arcade Cloud runs, and set ruff and mypy targets to match.
